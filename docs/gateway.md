# Getting SNOS online

Since the uIP cutover the console runs its own TCP/IP stack: it composes and
parses every IP header, resolves its own names, and opens its own
connections. The daemon on the other side of the link (`tools/gateway.py`)
is a **slirp box** — user-mode NAT, the QEMU arrangement — plus the link
peer itself. It routes the console's packets and understands none of them:
no fetch, no HTTP, no image conversion, no held sockets, three control verbs
(HELLO, and the port-forward pair IPFWD/IPUNFWD).

TLS is not part of this, permanently and on purpose. A TLS handshake on a
3.58 MHz 65816 runs to *minutes* before a byte of payload moves, and back in
the day it wouldn't have existed anyway. Anything that genuinely needs a
modern brain — TLS, page rendering, image conversion — becomes an ordinary
plain-HTTP service the console's own client calls (M12), not a privileged
box on the packet path.

## One-time setup

Mesen's Lua sandbox blocks file and process access by default, and the bridge
needs it (there is no socket library — `require("socket")` fails even with
access on, which is why a separate program does the networking).

> **Debug → Script Window → "Allow access to I/O and OS functions"**

Turn it **off again when you are done**. It grants file and process access to
*any* Lua script you subsequently run, not just this one.

## Running it

```sh
cd snos/snes
python3 tools/gateway.py          # leave this running
```

Then in Mesen: load `snos.sfc`, open **Debug → Script Window**, and load

```
snos/snes/build/snosbridge.lua
```

and press **Run**. Mesen runs one script at a time, so that file deliberately
contains *both* the keyboard bridge and the gateway bridge — loading it does not
cost you the other. It is regenerated by every `make`.

In SNOS:

```
net status          probe the daemon (HELLO round trip), address, counters
net test            reach a known host over the console's own TCP
ping HOST           four real ICMP echoes, composed on the 65816
resolve NAME        the console's own DNS query
netecho [PORT]      echo server (default 7777)
httpd [PORT]        serve the volume over HTTP (default 8080)
get URL -           fetch over HTTP and print to the console
get URL NAME        fetch and save to the SRAM volume
view NAME           display a picture
```

`get` is a real HTTP/1.0 client: the request line goes out over the
console's TCP, and the status line and headers come back as bytes it parses
itself. `http://` only — `https://` is refused with its reason rather than
attempted and failed obscurely. It requires a destination: `-` means the
console; anything else is a file.

There is no image conversion anywhere on the path any more. What the server
sends is what lands, byte for byte — a ready-made `.IMG` (Mode 3 tiles)
downloads like any other file and `view` shows it, which is exactly the M12
shape: conversion as an ordinary HTTP service somewhere else.

`get` and `view` are applications, not shell builtins. Typing an application's
name runs it, so no `run` prefix is needed.

## Why two files instead of a socket or a pipe

Mesen's Lua has no sockets, so the process that opens them has to be a separate
one and something must carry bytes to it. A FIFO is the obvious choice and the
wrong one: a blocking read inside an `endFrame` callback freezes the emulator.
Reading a regular file at a tracked offset returns whatever is there and never
blocks, which is the property that matters.

`/tmp/snos-up.bin` and `/tmp/snos-down.bin` grow for the length of a session.
**Only the bridge truncates them**, when the emulator starts a session. The
daemon joins the stream where it finds it — it seeks to the current end of the
up-file and appends to the down-file — and the bridge resets its read offset if
it ever sees the file shrink underneath it.

That division matters. When both ends truncated, restarting the daemon silently
invalidated the offset the bridge was reading from, so the SNES never saw
another frame and no amount of reloading the script helped. Two truncators, one
pair of files, no protocol between them.

## The gateway must not free-run

It emits **exactly one frame per frame received**. This is not a throttle, it is
the protocol: the real link is clocked by the SNES, so the gateway physically
cannot transmit unless an exchange happens.

An earlier version emitted a frame every 4 ms "so acks keep flowing". Its loop
ran at 250 Hz against a console polling at 60, so the down file grew four times
faster than it was consumed; the bridge fell permanently behind, read frames
from minutes earlier, and the file passed two megabytes in about two minutes. A
file bridge that free-runs is not the same protocol as the cable, and would hide
exactly the bugs that only appear on hardware.

(The NAT is the one thing that moves on wall-clock time rather than the
console's polling — a socket becomes readable when it becomes readable — so
`slirp.tick()` runs every loop pass. Its *output* still rides the one-frame-
per-frame rule like everything else.)

## When it does not work

**"no link attached"** — the bridge has not claimed the link. It re-asserts
the magic word every frame precisely because `link_init()` zeroes the mailbox
*after* the script starts; if you see this persistently, the script is not
running.

**Anything at all — run `net status` first.** It sends a HELLO and waits for the
answer, so it reports the far end rather than the mailbox:

```
gateway alive @ 172.16.1.20, v2, replied in 5 frames    both halves are up
ip 10.0.2.15 via 10.0.2.2 (slirp), dns 10.0.2.3         ...and NAT is armed
no answer in 3s. N frames in, M resends                 bridge up, daemon not
no link (the bridge script is not running)              nothing claimed the mailbox
```

The daemon-not-answering line is the one worth having. `net_up()` only tests
whether the *bridge* claimed the link, so the old status said "gateway up"
while everything was timing out — a status line that is right only when
nothing is wrong, which is exactly when nobody reads it.

**"no ip - daemon did not claim NAT (vN); nothing will connect"** — the far
end answered HELLO but with a version below 2. Since the cutover there is no
stream fallback: a pre-NAT daemon can keep the link up and still carry no
traffic, and `net status` saying so beats every application failing one by
one. Run the current `tools/gateway.py`.

`net status` also prints the stack's own counters (what uIP made of the
datagrams the link moved) and the resolver slot's state — the resolver is a
single shared slot, so "what is it doing" is a real question when a by-name
connect will not start.

**`get` timing out** prints the link counters beneath the message. Non-zero
frames in means the link ran the whole time and the answer specifically went
missing (DNS, or the far host); zero means nothing crossed at all. Different
bugs, and they used to look identical.

**Either end can now be restarted alone**, which used to deadlock the link
permanently. The peer comes back at sequence zero while the other side is still
waiting for sequence 200, rejects every frame, never acks, and stop-and-wait
resends the same frame forever; only rebooting the SNES recovered. Fixed with
two rules that are both required, since each alone fixes one direction:

- `LINK_F_SYN` announces "my sequence begins again here", and the peer adopts it
  once per episode — once, because honouring it on every frame would re-deliver
  retransmissions, which the ordinary sequence check is what discards.
- A side that has just restarted **adopts the peer's sequence** from the first
  frame it sees. The peer has no reason to restart just because we did.

A daemon restart also drops the console's IP mode until the new process
answers HELLO for itself, fails every open channel (the NAT table those
connections lived in is gone), and resets the datagram framing — the console
counts a mid-datagram loss in `net status`'s `desync` field.

**The script produces no output whatsoever, and Mesen looks hung** — that is
what a Lua *syntax error* looks like in Mesen. There is no error message.
Suspect syntax before anything else; it has cost hours twice.

**A key does nothing** — check Mesen's own input bindings first. It consumes
keys bound to a controller button or a hotkey before any script sees them.
Backspace is bound by default, and F1–F11 are taken by the debugger, which is
why the break key is F12.

**Controller-driven tests fail claiming the keyboard is broken** — `make test`
checks for this now. Mesen resets `Snes.Port1.Type` to `None` when it exits, and
with no controller `emu.setInput` has nothing to set.

**The daemon seems to stop rather than fail** — send it SIGUSR1; it dumps its
stack. That settled, in one look, a starvation hunt that had cost an
afternoon of guessing.

## Security

The SNES↔daemon hop is plaintext. Over a cable in your house that is fine, but
it is a decision rather than an oversight.

The daemon's own traffic reaches it through a file the bridge writes, so it
cannot accidentally become an open proxy on your network. It no longer makes
any request on the console's behalf — it routes the console's own packets,
which leave wearing this host's address exactly as a QEMU guest's do. The
only sockets it listens on are the port forwards SNOS applications ask for
(`httpd 8080` and friends). Those bind `0.0.0.0` deliberately — the point is
a SNES serving a page to someone else's phone at a conference — and that IS
an exposure decision: what a SNES app serves becomes reachable by anything
that can route to this host. Set `SNOS_LISTEN_ADDR` (read by `slirp.py`) to
`127.0.0.1` to keep it to the machine.

## Servers: the SNES accepting connections

Two applications, and the reason there are two is that `netecho` has no parsing
in it — if something is broken, it is the channel API and not the program.

```sh
# on the SNES
netecho                       # then: nc <daemon-ip> 7777, type, see the echo
httpd                         # then: curl http://<daemon-ip>:8080/
```

`net status` prints the address to use. The console's own address exists only
on the SNES↔daemon link — behind the NAT, by design — so everything it serves
is reached at the daemon host's address, through a real socket the daemon
holds on the console's behalf (the IPFWD forward). uIP binds the port on the
console; the daemon's socket is the only thing it contributes to an inbound
connection.

**Ports below 1024 need root**, because the daemon binds the forward. That is
why the defaults are 7777 and 8080 rather than 7 and 80; `httpd 80` works if
you started the daemon with privileges.

**One connection at a time, per port.** A second SYN on a bound port is
refused while a connection is being served — two clients interleaved into one
channel's rings would corrupt both — and the server loops back to LISTEN
between requests, so the refusal window is one request long. `curl`, `nc`,
and a phone loading one page all work. A desktop browser opens six
connections at once and will look broken — that is the design, not a bug.

**`httpd` is GET-only, HTTP/1.1, `Connection: close`.** No keep-alive, chunking,
compression, ranges or conditional requests. `/` means `INDEX.HTM`; anything with
a `/`, `%` or `\` in it is refused, because the volume is flat so a separator is
either a mistake or an attempt to leave. Content-Type comes from the extension.
Files come from the same volume as everything else, so `edit INDEX.HTM` and
reload is the entire authoring workflow.

### The half-close, which cost the most time here

`printf 'hi' | nc` and many HTTP clients do the same thing: send the request,
then **close their sending side and wait to read**. Layers of this system
have repeatedly treated that as "the connection is over" — in the stream-
gateway era it was the daemon's pump and `net_write` (both fixed, both
lessons recorded here at the time), and in the uIP era the limitation is the
stack itself:

**uIP 1.0 has no CLOSE_WAIT.** A FIN arriving on an established connection
makes uIP FIN straight back and close both directions at once, so a server
application can never send its reply after the client's FIN has been
processed — the reply races the FIN, and loses as often as not.

The daemon absorbs that, because it terminates the outside client's TCP
itself: for **inbound forwards** it holds the client's FIN back until the
console's replies have gone quiet for a moment (`FIN_GRACE`, 0.75 s, in
`slirp.py`). The echo leaves first, then the FIN lands, netecho sees EOF and
loops. Outbound flows keep prompt EOF delivery — `get`'s end-of-body IS the
far server's FIN, and a grace there would tax every fetch.

`NET_ST_EOF` is still a state an app serves from rather than one it bails
out on: EOF means the *peer* stopped sending, and the direction you write in
is still open — at the channel API. Just get the reply queued before
relying on it.

### Hanging up without truncating

`sys_net_hangup(ch)` ends the current connection and keeps the port — the app
loops instead of re-binding, and a straggler cannot steal it between requests.

It **refuses while bytes are still queued or unacknowledged**, and the caller
retries. That is not politeness: the close it triggers is uIP's graceful FIN,
and a FIN that overtook the response's last segment would truncate what the
client receives — the exact thing this call exists to prevent. (An abort
path would be a RST, which lets the client discard response bytes it has
received but not yet read; that is why the graceful path exists at all.)

## `irc` — the SNES on IRC

```
irc HOST[:PORT] [NICK] [#CHANNEL]      port defaults to 6667, nick to 'snes'
```

An outbound `sys_net_connect` and nothing else. The connection is the
console's own TCP through the NAT; the daemon routes packets and knows
nothing about IRC. Line-oriented ASCII is the one thing this link and this
console are both actually good at.

**It is a text application.** It never touches `sys_gfx` and never takes the
PPU: no shadow framebuffer, no tiles, no write window, no OAM. It paints the
console with `SYS_PUTS_AT`, which cannot scroll, so the layout holds still with
no HDMA split — a tab bar on row 0, the message pane in the middle, the input
line on the last row. The keyboard panel needs a split because it coexists with
a *scrolling* console; this replaces the console outright.

The consequence is that pane scrolling is a repaint of every pane row, since the
console's own scroll would carry the bar and the input line with it. That is
also why the user list is a **toggled overlay** rather than a side panel: a side
panel would be repainted by every single message.

| Key | |
|---|---|
| `^N` / `^P` | next / previous window (also left/right on the d-pad) |
| `TAB` | window switcher; digit or up/down, enter picks, esc closes |
| `^U` | user list overlay |
| `^Q` | quit |

`/join #c`, `/part`, `/msg nick text`, `/nick n`, `/names`, `/close`,
`/raw LINE`, `/quit [reason]`, `/help`. Anything not starting with `/` is sent
to the current window. PMs are just windows.

### Protocol decisions that are not negotiable

- **No `CAP LS`, ever.** Undernet and DALnet answer `421`; QuakeNet answers with
  *silence*. A client that sends it and waits for the list hangs on three
  networks, and there is nothing here that would use a capability.
- **`PING` is answered from the top of `handle_line`**, before anything else can
  return early. A missed `PONG` is not an error at the time — it is a silent
  disconnection several minutes later.
- **A `PRIVMSG` or `NOTICE` whose text starts with `\x01` is dropped.** OFTC
  sends an unsolicited CTCP VERSION on connect, and `\1VERSION\1` in the message
  pane looks exactly like the link corrupting data.
- **A tab is opened by the server's `JOIN` echo, not by typing `/join`.** A
  channel that is invite-only or full then never leaves an empty window behind.
- `sys_net_hangup` is **not** used on the way out. It applies only to a
  *listening* channel (`kernel/net.c` refuses otherwise), so a client would spin
  on it. `irc` waits for its own send queue to drain instead, which is what stops
  the `QUIT` being truncated into a dropped connection.

### A test server on your own machine

```sh
docker run -d --rm --name snosircd -p 6667:6667 ergochat/ergo   # plaintext :6667
docker stop snosircd
```

`ircd/unrealircd` does **not** work as published: its image entrypoint is a
single quoted string (`"…/unrealircd -F"`) and the container fails to start.
`ergochat/ergo` has no `:stable` tag on Docker Hub and is not published to
`ghcr.io` publicly — plain `ergochat/ergo` is the one that pulls. It generates a
config and a self-signed cert on first run and listens on 6667 without one.

Point a bare `nc` or a five-line Python client at it before the SNES, so you are
debugging one side at a time. `testnet.ergo.chat:6667` explicitly invites client
testing if you would rather not run anything.

### Automated coverage

`make test-irc` runs a **Lua ircd** on the far side of the emulated link
(`test/irc.lua`, on the hermetic slirp box in `test/gwip.lua`) — the real
protocols, both of them: the ircd's lines ride real TCP segments that the
console's own stack acknowledges. It asserts registration without `CAP`, that
a server `PING` is answered, `JOIN` and the `NAMES` reply, a message in each
direction, that the CTCP between two ordinary messages is dropped while both
neighbours are displayed, that server traffic and channel traffic land in
*different* windows, that `^P`/`^N` move between them, and that `QUIT`
carries its reason.

## `vnc` — a Super Nintendo as a thin client

The console speaks RFB itself: handshake, pixel format, framebuffer updates,
pointer events. Nothing on the far side knows it is talking to a SNES — and
since the cutover the TCP under the RFB is the console's too.

```
vnc HOST[:PORT]        default port 5900

  arrow keys   move the cursor     space   click
  W A S D      pan the window      ESC     quit
```

### Running it locally, start to finish

**1. Build the test server, once.** Needs Docker running.

```sh
cd snos/snes/tools/vncbox
docker build -t snos-vnc .
```

**2. Start it.** Either a browser or an xterm, on port 5900:

```sh
# a real browser on a 512x384 desktop, twice the console in each direction
docker run -d --rm --name snosvnc -p 5900:5900 \
  -e SNOS_APP=chromium -e SNOS_URL=https://news.ycombinator.com snos-vnc

# or a plain X session with an xterm (lighter, starts instantly)
docker run -d --rm --name snosvnc -p 5900:5900 snos-vnc
```

The desktop size is one line — `GEOM` at the top of `tools/vncbox/start.sh` — and
it is meant to be tuned by feel. It must stay a multiple of 8 in both axes.

Give chromium ~10 seconds to paint before connecting.

**3. Start the gateway** and load the bridge in Mesen as usual:

```sh
cd snos/snes && python3 tools/gateway.py
```

Then in Mesen: **Debug → Script Window**, load `snos/snes/build/snosbridge.lua`,
press Run. (Debug → Script Window → "Allow access to I/O and OS functions" must
be on, as for any networking here.)

**4. In SNOS:**

```
vnc 127.0.0.1
```

`127.0.0.1` and not `host.docker.internal` — the gateway runs on the host, and
that name only means anything *inside* a container.

### What to expect

The first screen is a full 48 KB framebuffer. **The 30-seconds-at-60 Hz
figure in the performance notes was measured in the stream-gateway era**; the
same bytes now ride the console's own TCP, whose single-segment stop-and-wait
adds round trips, so expect somewhat longer in the emulator and re-measure
before quoting a number. It **paints progressively**, one server rectangle at
a time, so you watch it arrive either way. (This is an emulator-rig cost, not
a hardware one: PLAN.md's performance section is the long story.)

After that, updates are incremental — a still screen sends **nothing at all**,
measured. Anything that changes sends only the rectangles that changed.

The bottom 32 scanlines are black. The picture is 192 lines of a 224-line
display, and that strip is not just leftover: it is where every VRAM and OAM
write happens (see below), so it has to stay black.

Arrow keys move the cursor and space clicks, from **either** a host keyboard
through the bridge or a controller d-pad. Typing does not work yet.

### Panning: the console is a window, not the desktop

At 256 CSS pixels Chromium wraps a page into a column too narrow to read, so the
desktop is 512x384 and the console shows a 256x192 **window** into it. WASD moves
the window by 32 pixels. Nothing is scaled — a server pixel is still a console
pixel, and the glyphs are the size they always were.

**A pan does not re-download the screen.** The client keeps its 48 KB shadow as a
torus — server pixel `(x, y)` always lives at shadow byte `(x mod 256, y mod 192)`
— so 32 pixels is four whole tiles and the part of the screen you keep needs no
pixel moved and no tile rebuilt. Only the tilemap is rotated, and only the strip
you have never seen is fetched, with a non-incremental request for exactly that
rectangle. (The pan timings recorded in PLAN.md's performance table are
stream-era numbers too.)

Clicks go out in **server** coordinates — pan origin plus cursor — so space keeps
hitting what is under the arrow after you have panned. `PAN_STEP` in
`apps/vnc/vnc.c` is the step size and must stay a multiple of 8; anything else
cannot be expressed in a tilemap and would cost a full 768-tile rebuild per pan.

### Sanity checks if it does not work

`net status` first: it probes the daemon and reports the link and stack
counters, so it separates a dead daemon from a dead link from a stack that is
dropping datagrams.

```sh
python3 snos/snes/tools/rfbspike.py 127.0.0.1 5900
```

That is a throwaway Python RFB client. If it reports `OK: ... exactly 1 byte per
pixel` then the server and the pixel format are fine and the problem is on the
console side. It also renders what the SNES would display if you pass it an
output path.

### If the picture is noisy or flickers

Almost certainly a display register, not the network — the bytes reach VRAM
correctly and something else spoils how they are read. Capture it:

```sh
cd snos/snes
cat build/snosbridge.lua tools/vramwatch.lua > /tmp/watch.lua
```

Load `/tmp/watch.lua` in the Script Window instead of the bridge — the bridge is
included, so everything still works — and read the log while `vnc` runs.

**`$420C` non-zero while the app is running is the answer.** That is the keyboard
panel's HDMA still rewriting the BG tilemap base every scanline, which makes the
PPU fetch tiles from the wrong address: flickering noise over a picture that is
correct in VRAM. `$2115` should read `80` whenever tile data is being written.

**`$2100` toggling between `8F` and `0F` many times a second is EXPECTED** and is
not the flicker. It used to be: the app held forced blank across a whole
rectangle's repaint and repaints once per rectangle, so the screen went black for
seconds at a time, several times a screen — 1242 frames of black in one measured
run. Now each blank lasts about twenty scanlines and lands entirely between
scanlines 192 and 224, below the picture, where nothing is displayed.

**Why blank at all, when the rule is "write VRAM in vblank"?** Because an
application does not get one. NMI moves a link frame on every frame while an app
owns the PPU — `con_dirty_pending()` returns 0 while `gfx_owned`, deliberately,
or the link dies mid-handshake — and at `-O0` that handler runs from the top of
vblank until about scanline 100 of the *next* frame. The first attempt at fixing
the flicker waited for vblank and `make test-vnc` caught it: every DMA landed at
scanline 104-122, in the middle of the picture, and the vblank check failed on 96
batches out of 96. `con_flush`'s ten-transfers-per-vblank budget only exists
because the kernel gets NMI out of its own way first.

**The same applies to OAM, and cost an afternoon.** A write to `$2104` during
active display does not go where `OAMADDR` points — sprite evaluation owns the
address counter — so `vnc`'s cursor never moved, while ESC (which is not an OAM
write) worked perfectly. It looks exactly like a lost keystroke, and it is not:
check the bindings and the key names once, then suspect the write.

### Automated coverage

```sh
cd snos/snes && make test-vnc
```

`test/vnc.lua` is a **Lua RFB server** on the hermetic slirp box — the real
protocols, RFB over real TCP segments, not a stub — and it asserts the two
failures above: the picture is checked by following the tilemap the way the
PPU does, and every forced blank is checked for falling inside the strip. It
also drives both input paths and reads the cursor back out of OAM. Not part
of `make test`: it moves a whole 48 KB framebuffer through the emulated link,
which takes as long as the other tests together.

### Known gaps

No keyboard yet — the cursor and clicks work, typing does not. `CopyRect` is
advertised to the server but its path has never executed; it will fire the first
time something on screen scrolls, and `make test-vnc` does not cover it either.

The transpose costs **1.3 frames per tile at -O0**, so a full screen is 17
seconds of CPU against 80 seconds of wire. Fine now; at M7's cable speed it
becomes the bottleneck, and it is the obvious candidate for hand-written 65816.


## `mc` — join a Minecraft server running on the console

The world is baked into cart ROM at build time (`tools/mkmc.py`); the 65816
streams it. Java Edition 1.16.5 exactly — the console advertises protocol
754 and other versions will refuse.

```
# on the SNES
mc            (or `mc &` to keep the shell; a join raises the notify cell)

# on your machine (or any machine that can reach it)
Minecraft 1.16.5 -> Multiplayer -> Direct Connect -> <the address
`net status` prints>   (localhost if the daemon runs on the same Mac)
```

What to expect: the server list shows "A Super Nintendo. Really." The join
burst is ~146 KB over a ~600 B/s emulated link, so "Loading terrain" takes
a few minutes (a real M7 cable would make it ~7 s); keepalives flow
throughout, so it holds. You spawn in creative on superflat grass facing a
stone SNOS. Chat echoes through the console (and appears on its screen),
and every block you punch is put back — the world is read-only, enforced
diegetically.

One player at a time, by uIP's listen design — but the port is bound by TWO
channels, because joining is two connections (the server-list ping, then
the login) and they overlap. `tools/mcprobe.py` serves the same baked bytes
from Python for protocol debugging at desk speed, and `gateway.py --debug`
hex-dumps every datagram when the wire itself is in question.

## The NAT (`tools/slirp.py`)

The daemon's whole understanding of traffic. It takes IPv4 datagrams the
console composed and moves them onto real sockets:

```
    10.0.2.15   the SNES        (constants, no DHCP -- there are two nodes)
    10.0.2.2    us: default route and NAT
    10.0.2.3    us: the resolver the console sends real DNS queries to
```

Traffic leaves wearing this host's address, exactly as a QEMU guest's does.
Inbound connections need a real socket on the console's behalf, which is what
`C2S_IPFWD` asks for — the console is behind the NAT and cannot be dialled
from the LAN.

Capability is stated in the HELLO version: **2 means "I do NAT"**, and since
the cutover it is the only kind of daemon the console works with — a v1
answer leaves `net status` saying so and nothing able to connect. An older
console against this daemon simply sends stream records this daemon steps
over by their length byte.

Hermetic coverage: `test/host/slirp_test.py` drives the NAT directly (ICMP,
UDP, the DNS front, TCP both directions, resets, forwards), and
`test/host/bridge_test.py` drives the file-relay discipline;
`test/gwip.lua` is the NAT's hermetic twin on the Mesen side, implemented
independently in Lua so the console's stack and the tests cannot share a
misunderstanding.

### Things that bit, and are now defended

- **`/etc/resolv.conf` can list IPv6 nameservers first.** This Mac does
  (`fe80::...%en0`). Handing one to an IPv4-only console is meaningless, and
  handing it to `inet_aton` raised — which killed the daemon's frame loop and
  took the whole link down. Non-IPv4 entries are skipped now.
- **Nothing the console sends may kill this process.** The link is the
  console's only voice; a daemon that dies on a surprising datagram removes
  the very channel that would have reported it. Both NAT entry points are
  wrapped, and log rather than exit.
- **macOS grants unprivileged ICMP datagram sockets** and returns the whole IP
  datagram on receive, where Linux returns the ICMP message alone and rewrites
  the identifier. Both shapes are handled; that is why `ping 8.8.8.8` works
  from a Super Nintendo without root.
- **uIP cannot half-close** (no CLOSE_WAIT), so an outside client that FINs
  right after its request would race the console's reply. For inbound
  forwards the FIN is held until the console's replies go quiet for
  `FIN_GRACE` (0.75 s); outbound flows deliver EOF promptly, because `get`'s
  end-of-body IS the far server's FIN.
