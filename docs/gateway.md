# Getting SNOS online

The SNES has no TCP/IP stack and never will. A gateway on the other side of the
link does DNS, TCP, TLS and HTTP, and hands the SNES plain bytes. It is a
forward proxy making ordinary, honest TLS connections as itself — nothing forges
a certificate, so there is no CA to install and nothing to trust on the SNES.

This is not a compromise for convenience. A TLS handshake on a 3.58 MHz 65816
runs to *minutes* before a byte of payload moves, so terminating TLS on the far
side is the only thing that makes IRC, HTTPS or anything modern reachable at all.

## One-time setup

Mesen's Lua sandbox blocks file and process access by default, and the bridge
needs it (there is no socket library — `require("socket")` fails even with
access on, which is why a separate program does the networking).

> **Debug → Script Window → "Allow access to I/O and OS functions"**

Turn it **off again when you are done**. It grants file and process access to
*any* Lua script you subsequently run, not just this one.

## Running it

```sh
cd snos/snes
python3 tools/gateway.py          # leave this running
```

Then in Mesen: load `snos.sfc`, open **Debug → Script Window**, and load

```
snos/snes/build/snosbridge.lua
```

and press **Run**. Mesen runs one script at a time, so that file deliberately
contains *both* the keyboard bridge and the gateway bridge — loading it does not
cost you the other. It is regenerated by every `make`.

In SNOS:

```
net status          probe the gateway (HELLO round trip), its address, counters
net test            fetch a known URL to prove DNS, TLS and the link work
web URL             browse: cursor, click, scroll
get render:URL NAME fetch a still picture of a page (testing)
netecho [PORT]      echo server (default 7777)
httpd [PORT]        serve the volume over HTTP (default 8080)
get URL -           fetch and print to the console
get URL NAME        fetch and save to the SRAM volume
view NAME           display a picture
```

`get` requires a destination. `-` means the console; anything else is a file.
It used to be two commands (`get` printed, `download` saved), which meant no way
to tell from a call site which one you had.

There is no `image` command. The gateway reads the response's Content-Type and
converts a picture to Mode 3 tile data on its own — it is the only party that
knows what came back and the only one that could decode it anyway. The saved
name is forced to `.IMG`, because the bytes are no longer the resource that was
requested.

`get` and `view` are applications, not shell builtins. Typing an application's
name runs it, so no `run` prefix is needed.

## Why two files instead of a socket or a pipe

Mesen's Lua has no sockets, so the process that opens them has to be a separate
one and something must carry bytes to it. A FIFO is the obvious choice and the
wrong one: a blocking read inside an `endFrame` callback freezes the emulator.
Reading a regular file at a tracked offset returns whatever is there and never
blocks, which is the property that matters.

`/tmp/snos-up.bin` and `/tmp/snos-down.bin` grow for the length of a session.
**Only the bridge truncates them**, when the emulator starts a session. The
daemon joins the stream where it finds it — it seeks to the current end of the
up-file and appends to the down-file — and the bridge resets its read offset if
it ever sees the file shrink underneath it.

That division matters. When both ends truncated, restarting the daemon silently
invalidated the offset the bridge was reading from, so the SNES never saw
another frame and no amount of reloading the script helped. Two truncators, one
pair of files, no protocol between them.

## The gateway must not free-run

It emits **exactly one frame per frame received**. This is not a throttle, it is
the protocol: the real link is clocked by the SNES, so the gateway physically
cannot transmit unless an exchange happens.

An earlier version emitted a frame every 4 ms "so acks keep flowing". Its loop
ran at 250 Hz against a console polling at 60, so the down file grew four times
faster than it was consumed; the bridge fell permanently behind, read frames
from minutes earlier, and the file passed two megabytes in about two minutes. A
file bridge that free-runs is not the same protocol as the cable, and would hide
exactly the bugs that only appear on hardware.

## When it does not work

**"no gateway attached"** — the bridge has not claimed the link. It re-asserts
the magic word every frame precisely because `link_init()` zeroes the mailbox
*after* the script starts; if you see this persistently, the script is not
running.

**Anything at all — run `net status` first.** It sends a HELLO and waits for the
answer, so it reports the far end rather than the mailbox:

```
gateway alive @ 172.16.1.20, v1, replied in 5 frames   both halves are up
link up, but the gateway is NOT answering  bridge running, daemon is not
no link (the bridge script is not running) nothing has claimed the mailbox
```

The middle line is the one worth having. `net_up()` only tests whether the
*bridge* claimed the link, so the old status said "gateway up" while every fetch
was timing out — a status line that is right only when nothing is wrong, which
is exactly when nobody reads it.

**"timeout waiting for the gateway"** now prints the link counters beneath it.
Non-zero frames in means the link ran the whole time and the reply specifically
went missing; zero means nothing crossed at all. Different bugs, and they used
to look identical.

**Either end can now be restarted alone**, which used to deadlock the link
permanently. The peer comes back at sequence zero while the other side is still
waiting for sequence 200, rejects every frame, never acks, and stop-and-wait
resends the same frame forever; only rebooting the SNES recovered. Fixed with
two rules that are both required, since each alone fixes one direction:

- `LINK_F_SYN` announces "my sequence begins again here", and the peer adopts it
  once per episode — once, because honouring it on every frame would re-deliver
  retransmissions, which the ordinary sequence check is what discards.
- A side that has just restarted **adopts the peer's sequence** from the first
  frame it sees. The peer has no reason to restart just because we did.

**The script produces no output whatsoever, and Mesen looks hung** — that is
what a Lua *syntax error* looks like in Mesen. There is no error message.
Suspect syntax before anything else; it has cost hours twice.

**A key does nothing** — check Mesen's own input bindings first. It consumes
keys bound to a controller button or a hotkey before any script sees them.
Backspace is bound by default, and F1–F11 are taken by the debugger, which is
why the break key is F12.

**Controller-driven tests fail claiming the keyboard is broken** — `make test`
checks for this now. Mesen resets `Snes.Port1.Type` to `None` when it exits, and
with no controller `emu.setInput` has nothing to set.

## Security

The SNES↔gateway hop is plaintext. Over a cable in your house that is fine, but
it is a decision rather than an oversight.

The daemon **listens on no socket** — traffic reaches it through a file the
bridge writes, so it cannot accidentally become an open proxy on your network.
Worth keeping that way if it ever grows a socket for convenience.

## Servers: the SNES accepting connections

Two applications, and the reason there are two is that `netecho` has no parsing
in it — if something is broken, it is the stream API and not the program.

```sh
# on the SNES
netecho                       # then: printf 'hi\n' | nc <gateway-ip> 7777
httpd                         # then: curl http://<gateway-ip>:8080/
```

`net status` prints the address to use. The SNES has none of its own — it has no
IP stack, which is the premise of the whole design — so everything it serves is
reached at the gateway's address.

**Ports below 1024 need root**, because the gateway binds the socket. That is
why the defaults are 7777 and 8080 rather than 7 and 80; `httpd 80` works if you
started the daemon with privileges.

**One connection at a time.** There are three channels in total and the link
moves ~615 B/s. `curl`, `nc`, and a phone loading one page all work. A desktop
browser opens six connections at once and will look broken — that is the channel
count, not a bug.

**`httpd` is GET-only, HTTP/1.1, `Connection: close`.** No keep-alive, chunking,
compression, ranges or conditional requests. `/` means `INDEX.HTM`; anything with
a `/`, `%` or `\` in it is refused, because the volume is flat so a separator is
either a mistake or an attempt to leave. Content-Type comes from the extension.
Files come from the same volume as everything else, so `edit INDEX.HTM` and
reload is the entire authoring workflow.

### The half-close, which cost the most time here

`printf | nc` and every HTTP client do the same thing: send the request, then
**close their sending side and wait to read**. Two separate layers treated that
as "the connection is over":

- the gateway's pump closed the socket when `recv` returned empty, throwing away
  the response before it was written;
- `net_write` refused to queue bytes on a channel in `EOF` state, so the echo
  loop span forever waiting for space that would never come.

EOF means the *peer* stopped sending. The direction you write in is still open.
Both now say so, and `NET_ST_EOF` is a state an app serves from rather than one
it bails out on.

### Hanging up without truncating

`sys_net_hangup(ch)` ends the current connection and keeps the port — the app
loops instead of re-binding, and a straggler cannot steal it between requests.

It **refuses while bytes are still queued**, and the caller retries. That is not
politeness: `build_frame` packs the control queue *before* channel data, so a
hangup queued next to a half-sent response would overtake it and the client
would get a truncated page.

## Looking at the web: `render:`

```
get render:news.ycombinator.com HN
view HN.IMG
```

The SNES cannot lay out HTML — Wikipedia's SNES article is 735 KB against a
64 KB app arena, which is not a tuning problem — but it is genuinely good at
displaying a 256-colour bitmap, and the image path already exists for
photographs. So `render:` is the same division of labour as TLS and JPEG
decoding: the far side does what the 65816 cannot, and the console does what it
is good at. **No SNES code was written for this.** The bytes arriving are
ordinary Mode 3 tiles and `view` has no idea a browser was involved.

**512x448, not 256x224.** Rendering at the console's own resolution turns body
text into a grey smear. Rendering at double and letting `to_img` downscale 2:1
keeps the greyscale antialiasing that makes 4-pixel-wide glyphs readable —
supersampling, and it is the difference between "you can tell those are words"
and "you can read them". 512x448 is exactly twice 256x224, so the Lanczos step
is a clean 2:1 with no aspect correction.

Chrome is **optional**. Everything else here runs on the standard library plus
Pillow; missing Chrome gives "no renderer configured" rather than a traceback.
Set `SNOS_CHROME` to override the binary.

### Two things that cost an hour, worth keeping

**A throwaway `--user-data-dir` is not optional.** Without it Chrome uses the
real profile — rendering pages with the user's live cookies, sending their
logged-in session to whatever the SNES asked for, and fighting their own running
browser for the profile lock.

**But with it, Chrome writes the PNG and then never exits.** So the renderer
waits for the FILE to appear and stabilise and then kills the process itself.
Waiting on the process hangs forever, which is exactly what the first version
did.

### What it costs

A screenful is ~57 KB of tiles: **94 seconds at 615 B/s, about 3 seconds at
M7's 20 KB/s.** Rendering itself is 2.5-4 s. This is a demo that wants the
cable.

## `web` — the browser

```
web news.ycombinator.com

  arrow keys   move the cursor      space   click
  W / S        window up / down     ESC     quit
  A / D        back / forward
```

Chrome runs on the far side and stays **open** for the session — a click needs
the same document the screenshot came from, and scrolling needs the page's own
scroll position. A fresh browser per request could screenshot but never
interact. `tools/browser.py` drives it over CDP.

The console never sees HTML. It gets Mode 3 tiles, exactly as a photograph would
produce, and moves a sprite over them. **That is what makes the cursor free** —
a sprite moves by writing four bytes of OAM, with no repaint, no tile churn and
no DMA. Moving a cursor by rewriting the bitmap would cost a whole window per
step.

Clicks are resolved to a link and navigated rather than synthesised as a mouse
event: a real click can land on an overlay, open a tab, or run script that goes
nowhere, and none of those have anywhere to go on a SNES. Clicking something
that is not a link does nothing, which is the honest outcome when the console
cannot show what it hit.

### Why a hand-written WebSocket

CDP commands are websocket-only — the HTTP endpoints can list targets but
cannot evaluate or click — and Python has no websocket client in the standard
library. `gateway.py`'s one virtue as a dependency is needing nothing but
Pillow, so `browser.py` carries about eighty lines of RFC 6455 client instead.
Cheaper than a dependency, much cheaper than being unable to click.

### Two things that are not obvious

**`--window-size` is not the CSS viewport.** Headless Chrome asked for 512x384
returns a 512x241 screenshot. `Emulation.setDeviceMetricsOverride` pins it;
without that, `to_img` letterboxes a short image into a tall window and the page
arrives squashed into the middle of the screen.

**The window is 192 lines, not 224.** A full-screen 8bpp image is 57 KB of tiles
and the sprite tile base can only sit on a 16 KB boundary — every one of which
lands inside an image that large. Giving up 32 scanlines buys a cursor with no
overlap and no corrupted block. v2's 4-colour format makes tiles 16 bytes rather
than 64 and frees over 30 KB, so this is temporary.

### What it costs, and what v2 fixes

Every action is a whole window: ~49 KB, **80 seconds at 615 B/s, about 2.5 at
M7's 20 KB/s**. There is no partial update because the console has no model of
the page — it has pixels.

v2 sends unique tiles plus a tilemap and keeps a cache. Measured on a real page:
a scroll introduces only **~22% new tiles**, because a rendered page is mostly a
font and the glyphs are already resident. That is 8 KB instead of 49 KB per
scroll — and at 4 colours and 512 dots wide it is both smaller and sharper than
what v1 sends.

## `vnc` — a Super Nintendo as a thin client

The console speaks RFB itself: handshake, pixel format, framebuffer updates,
pointer events. Nothing on the far side knows it is talking to a SNES.

```
vnc HOST[:PORT]        default port 5900

  arrow keys   move the cursor     space   click
  ESC          quit
```

### Running it locally, start to finish

**1. Build the test server, once.** Needs Docker running.

```sh
cd snos/snes/tools/vncbox
docker build -t snos-vnc .
```

**2. Start it.** Either a browser or an xterm, on port 5900:

```sh
# a real browser at exactly the console's resolution
docker run -d --rm --name snosvnc -p 5900:5900 \
  -e SNOS_APP=chromium -e SNOS_URL=https://news.ycombinator.com snos-vnc

# or a plain X session with an xterm (lighter, starts instantly)
docker run -d --rm --name snosvnc -p 5900:5900 snos-vnc
```

Give chromium ~10 seconds to paint before connecting.

**3. Start the gateway** and load the bridge in Mesen as usual:

```sh
cd snos/snes && python3 tools/gateway.py
```

Then in Mesen: **Debug → Script Window**, load `snos/snes/build/snosbridge.lua`,
press Run. (Debug → Script Window → "Allow access to I/O and OS functions" must
be on, as for any networking here.)

**4. In SNOS:**

```
vnc 127.0.0.1
```

`127.0.0.1` and not `host.docker.internal` — the gateway runs on the host, and
that name only means anything *inside* a container.

### What to expect

The first screen is a full 48 KB framebuffer: **about 80 seconds at the
emulator's 615 B/s**, and roughly 2.5 at M7's cable speed. It paints in one go
when it arrives rather than progressively, because a tile cannot be built from
part of a rectangle.

After that, updates are incremental — a still screen sends **nothing at all**,
measured. Anything that changes sends only the rectangles that changed.

### Sanity checks if it does not work

`net status` first: it probes the gateway and reports the link counters, so it
separates a dead daemon from a dead link.

```sh
python3 snos/snes/tools/rfbspike.py 127.0.0.1 5900
```

That is a throwaway Python RFB client. If it reports `OK: ... exactly 1 byte per
pixel` then the server and the pixel format are fine and the problem is on the
console side. It also renders what the SNES would display if you pass it an
output path.

If the gateway ever seems to stop rather than fail, **send it SIGUSR1** — it
dumps every thread's stack. That is how the starvation bug that blocked this app
for an afternoon was finally found, after a great deal of guessing that a stack
trace would have settled immediately.

### If the picture is noisy or flickers

Almost certainly a display register, not the network — the bytes reach VRAM
correctly and something else spoils how they are read. Capture it:

```sh
cd snos/snes
cat build/snosbridge.lua tools/vramwatch.lua > /tmp/watch.lua
```

Load `/tmp/watch.lua` in the Script Window instead of the bridge — the bridge is
included, so everything still works — and read the log while `vnc` runs.

**`$420C` non-zero while the app is running is the answer.** That is the keyboard
panel's HDMA still rewriting the BG tilemap base every scanline, which makes the
PPU fetch tiles from the wrong address: flickering noise over a picture that is
correct in VRAM. `$2115` should read `80` whenever tile data is being written.

### Known gaps

No keyboard yet — the cursor and clicks work, typing does not. `CopyRect` is
advertised to the server but its path has never executed; it will fire the first
time something on screen scrolls.
